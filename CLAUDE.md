# NamibWay (working repo name: travel-platform)

AI-assisted travel planning & booking platform for Namibia. Domain: namibway.com.
Slogan: "The smartest way to experience Namibia."

## What this is
A conversational, magazine-style travel platform. Instead of search forms, travelers chat with an AI travel companion ("Kaia") that interviews them and generates a bookable, multi-part itinerary (accommodation + activities + restaurants + vehicle + routing). A classic filter/search UI ("Explore") exists as a secondary path for browsing. The platform then manages the request/booking flow with partners (lodges, activity operators, restaurants), and offers after-sales support (checklist, on-trip help, feedback).

## Current focus — the Kaia trip plan (Reiseplan)
**This is the product.** It's what differentiates NamibWay from every filter-and-list competitor, and it's where effort goes right now. When prioritising work or trading off scope, the trip plan wins.

What "good" means here, in the order it gets judged:
- **Ergonomics & usability** — planning has to feel effortless: few taps, obvious next step, nothing that needs explaining.
- **Fun to use** — planning a trip should be enjoyable, not a form to fill in. Delight is a feature, not polish-later.
- **Reliability** — no lost plans, no half-generated itineraries, no dead ends. A plan the traveler can't trust is worse than no plan.
- **Responsiveness across every surface** — mobile browser, PWA, and the iOS/Android Capacitor apps are first-class, not adaptations of a desktop layout. Test mobile viewports and the native shells, not just a wide browser.
- **Looks** — magazine-quality visual quality; the plan is what people screenshot and share.

**Direction of travel: the plan becomes collaborative.** A trip is rarely planned by one person, so a plan is meant to be shared with fellow travelers who can join in — shared **read-only or with write access**, co-planning or commenting, with follow-ups on comments and a log of who changed what. Today's sharing is a single link that is implicitly full-write (`SavedPlan` token; `KaiaController::updatePlan` authorizes nothing beyond knowing the token, and the recorded `user_id`/`session_id` are unused), and there are no participants, comments, or history — so this is a real data-model step, not a UI toggle. Build new plan features so they don't have to be torn up for it: assume a plan has multiple people with different permissions, and that every change is attributable. Shape and open questions: `TRAVEL_PLAN.md` → "Future concept: collaborative trip plan".

**Where the account line sits.** Getting a plan and playing with it costs nothing — an account is only required once the plan becomes *durable, shared, or real*:
- **No account:** everything straight out of the Kaia chat — viewing the generated plan and editing it (swap items, reorder days, change trip params). This runs on the `SavedPlan` token and must stay frictionless; it's the first impression of the product.
- **Account required:** saving a plan to your account, collaborative editing (a co-planner is a person, so they need an identity), and booking.
- **Booking is the creator's alone, for now.** A shared plan does not turn co-planners into bookers — this keeps the one-active-request-per-traveler governance below coherent, which assumes exactly one responsible person per pipeline.

All three are enforced server-side since 2026-08-08. Creating and autosaving a plan still need no account, but an anonymous request can only produce an *unowned* plan; `KaiaController::claimPlan` (behind `auth`) is the only thing that writes `SavedPlan.user_id`. The booking endpoints (`ListingController::storeInquiry` / `storeBatchInquiry`, `TripController::store`) are behind `auth`, booking resolves "creator" from the plan's **edit** token — a read-only share token is refused — and the one-active-request gate matches on the account as well as the email (`App\Services\Booking\ActiveRequestGate`), so it can't be sidestepped by typing a second address.

`TRAVEL_PLAN.md` is the working log for exactly this — read its "Known gaps / next up" before starting, and add a dated entry when you finish something.

## Language — everything shipped is English
**English is the project language, without exception**: code, comments, commit messages, docs, UI copy, emails, the Filament admin and partner panels, and internal tools like the Excel capture workbook. This is not only about travelers — the team operating the platform (content managers, partner support) is English-speaking, so an internal-only screen or file is no reason to switch. The traveler-facing UI is additionally translated via `resources/js/lang/*.json` and translatable content columns (see "Multilingual" below), but English is what gets written first and what everything falls back to. ## Tech stack (decided — do not re-litigate without discussion)
- **Backend:** Laravel 12 (PHP 8.4)
- **Frontend:** Vue 3 + Inertia.js + TypeScript + Tailwind CSS 4, Vite build; Leaflet (+ markercluster) for maps, vuedraggable for the day list, vue-i18n for UI strings
- **Database:** PostgreSQL (17 in CI)
- **Admin/content CMS:** Filament — two panels: `/admin` (`AdminPanelProvider`) for the team, `/partner` (`PartnerPanelProvider`) for partner-scoped listing/inquiry management
- **Auth:** Fortify (incl. 2FA), Socialite (Google/Facebook), passkeys
- **AI:** Claude API via `App\Services\Kaia\AnthropicClient` — structured output / forced tool calls, same pattern as Wisherful
- **Queue/rate-limiting:** Laravel Queues + Redis + Horizon (Supervisor-managed)
- **Media storage:** Cloudflare R2 (`r2` disk). Legacy uploads on the local `public` disk predate 2026-08-02 — see `Controller::resolveMediaUrl`. Originals are the only stored truth; thumbnails are derivatives made on demand by `/thumbs/{width}/{key}` (`ThumbnailController` + `ThumbnailGenerator`), cached in the same bucket under `thumbs/` and served by redirect, so image bytes never pass through PHP. That prefix is a cache — deleting it is safe and is how a changed width ladder is applied. Cloudflare Image Transformations are an optional upgrade that takes precedence when available, but need a custom domain on the bucket, which needs namibway.com's DNS at Cloudflare (it's at OVH) — see `config/media.php`, DEPLOYMENT.md → "Bild-Thumbnails". The render width is a property of the component, not of the payload (`App\Support\MediaUrl` / `resources/js/lib/media.ts`)
- **Backups:** spatie/laravel-backup → separate **non-public** R2 bucket (`r2-backups`), AES-256 encrypted, nightly 02:00, failure-only mail notifications. `restore.sh` is the counterpart to `deploy.sh` for a total server loss
- **PDF output:** Laravel PDF service (trip plan PDF, partner API guide, listings partner handbook)
- **Public API:** `/api/v1` (Sanctum + `EnsureApiClientActive`), documented with Scribe; `ApiClient` model gates access
- **Mobile apps:** Capacitor 8 shells for iOS + Android wrapping namibway.com, with an offline bootstrap page (`ios-shell/index.html`). PWA icons/splashes derived from `public/images/pwa/icon-512.png` — see `MOBILE_APPS.md`
- **Payments:** built 2026-08-12 behind one `PaymentProvider` interface — `demo` (works end to end with no account and no internet, and says on every page that it is a demonstration), `dpo` (DPO Pay by Network, the only candidate that operates in Namibia and settles in NAD) and `paystack` (implemented, but needs a South African entity settling in ZAR, so not the recommendation). Chosen with `PAYMENTS_PROVIDER`, default `demo`. **Stripe is ruled out** and the old "Phase 2: Stripe" line was wrong for this market: it does not onboard Namibian entities
- **Multilingual:** `config/locales.php` — `en, de, nl, fr, es`. Content is translatable via spatie/laravel-translatable (`Listing`, `Destination`, `RouteTemplate`), UI via `resources/js/lang/*.json`. Ships English-first
- **Deploy:** every push to `main` that passes CI auto-deploys — `.github/workflows/deploy.yml` triggers on the `tests` workflow completing with `conclusion == 'success'` on `main`, then SSHes into the server, `git pull origin main`, and runs `deploy.sh` (composer, npm build, migrations, cache rebuild, permissions, queue restart, PHP-FPM reload). There is no separate manual deploy step; a green `main` immediately ships to production.

Rejected alternative: Next.js/Payload — would require re-solving problems (AI integration, multi-tenancy, i18n, storage, PDF, payments, deploy) already solved in the team's proven Laravel stack. Not worth it for a solo 3-month build.

### Panel navigation — every group is alphabetical
**Items inside a navigation group are ordered alphabetically by their label, in both Filament panels, always.** A sidebar is a place people look things up, and the only order you can look something up in is the one you can predict from its name. This is enforced, not remembered: `App\Filament\Navigation\AlphabeticalNavigationManager` (bound over Filament's own `NavigationManager` in `AppServiceProvider`) sorts each group on the label, and `AdminNavigationTest` asserts it for every group of both panels. So **do not add `$navigationSort` to anything that lives in a group** — it does nothing, and it reads as a promise of an order that isn't kept. Give the screen a good `$navigationLabel` and it lands where people will look for it.

The two exclusions, both deliberate: the **ungrouped top-level items** (the partner panel's Calendar → Arrivals → Rates is the working day in sequence, not a lookup) still use `$navigationSort`; and the **groups themselves** keep the curated order declared in the panel provider, because that order is an editorial statement about what matters most.

While you're in there: an icon means one thing across a panel — `heroicon-o-sparkles` is AI (Data Enrichment), so don't reach for it to mean "nice-to-have".

### Deploy incidents — fix `deploy.sh` itself, don't just patch the server by hand
When a production outage traces back to a flaw in the deploy process (not just a code bug), fix `deploy.sh` (or the deploy workflow) and note it here — don't only walk the user through one-off manual recovery commands.
- **2026-08-24:** the build depended on a font CDN staying up, and `deploy.sh` step 7 is where that would have been paid for. `vite.config.ts` declared its three families through the plugin's `bunny()` provider, which fetches `fonts.bunny.net` at *build* time. Twice in one afternoon it did not answer — a connection timeout on a CI runner (red check on a PR, no deploy) and a blocked host in a sandbox — and each failed `npm run build` outright. On the server that is an abort between `php artisan down` and `php artisan up`, which is precisely the 2026-08-09 shape: production sits at 503 until a human clears it, for a reason that has nothing to do with the code being deployed. Note the runtime was never exposed — the plugin self-hosts, emitting the files into the bundle — so this was only ever a build-time dependency, which is what made it easy to miss. Fixed by vendoring the six `.woff2` faces into `resources/fonts/` and switching to the `local()` provider, so no build reaches the network for a typeface. The general rule: **a deploy may not depend on a third party we do not pay, monitor or control** — anything a build fetches from one belongs in the repository or in `package-lock.json`. `resources/fonts/README.md` records why the obvious middle road (`@fontsource/*` npm packages) was rejected: they ship `.woff` beside `.woff2`, and the plugin's rule ordering makes the browser choose the larger one.

- **2026-08-11:** a new nginx vhost for the customer-website wildcard, handed over as a copy-paste block, took **every application on the server** down — namibway.com, the booking panel, and the iOS/Android shells with them, since those are wrappers around the live site. The block used `http2 on;`, which is nginx 1.25.1 and newer; this server is older and treats an unknown directive as fatal for the *entire* configuration, not just the file containing it. `nginx -t` failed and the `&&` stopped the reload, so nothing broke at that moment — but the symlink was already in `sites-enabled/`, and the next restart found a configuration nginx could not load. The lesson is not "check the nginx version": it is that **enabling a vhost and validating it must be one atomic step**, so a failed test can never leave a landmine for whoever restarts nginx next. `DEPLOYMENT.md` now enables every vhost as `ln -s … && nginx -t || rm <symlink>`, and says in the same breath that `ssl_certificate` pointing at a certificate that has not been issued yet fails exactly as hard.
- **2026-08-09:** recurring `touch(): Utime failed` 500s on individual views. `BladeCompiler::compile()` calls `touch($compiled, $mtime)` whenever a source view is newer than its compilation but byte-identical — which happens every deploy, because `scribe:generate` rewrites the docs view after `view:cache` already ran. `touch()` with an explicit mtime requires *ownership* (group write is not enough), and step 13's `chown -R $(whoami):www-data` handed every compiled view to the deploy user — so PHP-FPM (www-data) failed with EPERM forever after, 500ing every render of the affected view. Fixed by running `view:clear`/`view:cache` as www-data and re-chowning `storage/framework/views` to www-data after the global chown. Same day, separately: enabling `MEDIA_TRANSFORMS_ENABLED` + `CLOUDFLARE_R2_URL=https://cdn.namibway.com` in prod `.env` while that domain had no DNS record (namibway.com's DNS isn't on Cloudflare at all) 404'd every rewritten image; the code-side lesson — never rewrite app-origin/root-relative URLs through `/cdn-cgi/image/` — is baked into `config/media.php`/`MediaUrl`/`media.ts` now.
- **2026-08-04:** `deploy.yml` had no `concurrency` group, so two merges to `main` landing close together (observed 9 seconds apart) fired two overlapping `workflow_run` events, each SSHing into `/var/www/namibway` and running `deploy.sh` in parallel against the same directory — confirmed via the Actions run history (one of the two concurrent runs failed outright, run id `30813237154`, commit `701e4a3d`). Fixed by adding `concurrency: { group: production-deploy, cancel-in-progress: false }` to `deploy.yml` so overlapping runs queue and execute sequentially instead of racing. Note: this explains failed/racing deploy runs; it does NOT fully explain the separately reported symptom of "workflow shows green but the live site doesn't reflect the change" — if that recurs, suspect the same PHP-FPM/opcache class of issue as 2026-08-02, or a CDN/browser cache in front of namibway.com, and check the actual deployed commit on the server (`git -C /var/www/namibway log -1`) against `main`.
- **2026-08-03:** discovered `deploy.yml` triggered on every push to `main` regardless of the separate `tests` workflow's result — CI could be (and was) red and production would still redeploy. Changed the trigger from `push` to `workflow_run` (workflow: `tests`, `types: completed`), gated with `if: github.event.workflow_run.conclusion == 'success'`, so a failing `tests` run now blocks the deploy instead of racing it.
- **2026-08-01:** site-wide 500 (`Class "view" does not exist"`, root cause `Class "Laravel\Sanctum\Sanctum" not found`). `deploy.sh` decided whether to run `composer install` by checking `git diff HEAD@{1} HEAD` (the reflog) instead of the commit range actually just pulled — an unreliable check that skipped `composer install` on the deploy that added `laravel/sanctum`, leaving `vendor/laravel/sanctum` missing, which broke package discovery and cascaded into every service provider (including `view`) failing to register. Fixed by diffing `$OLD_COMMIT`..`$NEW_COMMIT` (captured directly around the `git reset --hard` in the deploy script) instead of the reflog, for both the composer.lock and package.json/package-lock.json checks.
- **2026-08-02:** a confirmed-correct PHP fix (a header-relocated Save button missing its `form` attribute) didn't take effect after deploying, because `deploy.sh` never restarted/reloaded PHP-FPM — only the Horizon queue worker (`supervisorctl restart`). With `opcache.validate_timestamps=0` (or just stale opcode caching in general), the FPM workers kept executing pre-deploy bytecode indefinitely for any changed PHP file, no matter how many times `git pull`/`composer install` ran. Made worse by discovering the server runs **both `php8.3-fpm` and `php8.4-fpm` simultaneously** — reloading only one is a coin flip as to whether it's the one nginx actually proxies to. Fixed by reloading *every* running `php*-fpm` systemd unit (not just the first found) right after the Horizon restart, before `php artisan up` — non-fatal if none are found, since server setups can vary.

## Current state — what's actually built
The MVP foundation is live in production; work now is depth and polish, not scaffolding.

**Domain model** (`app/Models`): `Listing` (accommodation/activity/restaurant/vehicle, with `vehicle_category` splitting self-drive vs guided tour), `BookableUnit` (renamed from `RoomType` 2026-08-12 — a quad bike and a seat are not room types; see `BOOKING_BEYOND_ROOMS.md` §3.2), `MenuItem` + `InquiryItem` (a restaurant's menu and the lines of an order — see "What a restaurant is asked for" below), `Partner`, `Customer` (who a property sells to — see below), `Note` (polymorphic comments), `Inquiry`, `Trip`, `SavedPlan`, `Review`, `Region` (Namibia's 14 political regions) → `City` (the **address**: towns, villages and settlements, see `CityType`) and `Place` (the **tourism location** a traveller plans around — national park, private reserve, landmark, and the towns that are stops on a trip; see `PlaceType`). A listing carries both, and for a camp on Onguma they are not the same answer: its post goes to Outjo and its traveller is in Etosha. Everything Kaia routes on is a place — the day location, `place_driving_hours`, the trip map — which is what `cities.place_id` links. Parks lived in `cities` between 2026-08-18 and 2026-08-23; see `TRAVEL_PLAN.md` for why that was split back out → listings, `Destination` (curated destination cards — and since 2026-08-19 the **area** a place is grouped under: Onguma and Ongava sit in Etosha, Sesriem in Sossusvlei. The area is what a traveler is shown beside a place name; the political region stays internal), `RouteTemplate` + `RouteTemplateStop` (curated classic routes Kaia adapts instead of inventing routes freeform), `EnrichmentJob`, `ApiClient`, `PartnerMessage`, `SupportMessage`, `TripFeedback`, `ReleaseNote`, `DocumentCategory` + `Document` (the team's own filing cabinet — see below).

Three groups sit beside those and belong to the booking system rather than to the travel platform, listed separately because the list above was written before they existed: **the stay** — `Reservation` + `ReservationUnit` / `ReservationNight` / `ReservationGuest` / `ReservationCharge`, `InventoryBlock`, `BookableUnitCalendarDay`, `BookingSlot`, `RatePlan` + `RatePlanDay` / `RatePlanGuestAmount`, `GuestCategory`, `Charge`, `Promotion`, `Amenity`; **the money** — `Payment`, `Invoice` + `InvoiceSequence`, `PaymentIntent`, `PaymentSettings`; and **the website builder** — `Site`, `SitePage`, `SiteBlock`, `SiteImage`.

**Kaia** (`app/Services/Kaia`, `routes/kaia.php`, `config/kaia.php`): interview + itinerary generation. **Trip plan (Reiseplan)** — the flagship feature: `resources/js/components/home/ItinerarySection.vue` and friends (`TripMap`, `ItineraryLineItem`, `AlternativesPanel`, `RoomTypePicker`, `TripMeta`), saved/shared via `SavedPlan` tokens (`/trip/{token}`, no login required), PDF export. **Partner connectors** (`app/Connectors`, `app/Enums/ConnectorType`): ResConnect (ResRequest), NightsBridge, hopeCloud, NWR (concierge/manual), **Native** (NamibWay's own bookable inventory with real `BookableUnit` availability + soft holds), Wetu (content-only), Manual. `ConnectorFactory` resolves per partner; `ProcessInquiry` drives availability → reservation → confirmed/on-request.

**Content acquisition:** Python scrapers (`scripts/`, run via GitHub Actions) feed `data/scraped/`, imported via `providers:import` / the `namibway:scrape-*` commands. The enrichment pipeline (`app/Services/Enrichment`) then finds websites, extracts structured data with Claude, generates descriptions, sources photos via Google Places/OSM, and scores completeness. Partner claim invites (`ClaimInviteService`, `/claim/{token}`) let real owners take over a scraped listing.

**Bulk capture (Excel):** for real, manually researched data, the admin panel is the slow path — `App\Services\ImportExport` is the fast one. `ListingSheet` defines the columns once for both directions; the listings table has "Export to Excel" (respects the active filters) and "Empty template", and Content → Import listings uploads a workbook, shows a dry-run diff, and only then writes (`namibway:export-listings` / `namibway:import-listings` do the same from the CLI). Two rules are load-bearing and must survive any change here: **the only automatic update key is the `id` column an export writes** — a row without one that matches an existing name/slug is an error telling the person which id to type, never a silent update or a duplicate — and **an empty cell means "leave this field alone"**, with `—`/`CLEAR`/`EMPTY` as the explicit "empty it" marker. Coordinates are one paste-anything cell (decimal pair, Google-Maps link, degrees-minutes); the intended flow is to leave them blank, let `namibway:backfill-listing-coordinates` geocode from the address, then export what's still missing and fill only those in. Photos ride along as a ZIP of one folder per listing, named in the `photo_folder` column (`PhotoArchive`; a `cover*` file becomes `image`, the rest the gallery, uploaded to R2 under `listings/{slug}/` with `photos_source = Partner`) — naming a folder replaces that listing's photos, which is the one place the "empty cell" rule is deliberately an all-or-nothing swap. Room types live on a second `RoomTypes` sheet of the same workbook (`BookableUnitSheet` — the sheet keeps its name, because people have those files), matched on listing + `code` — the one natural key in this design — and can reference a listing the same import is creating; their photos are a folder inside the listing's folder (`room-types/{slug}/{code}/` on R2). A folder is matched on the tail of its path, so `Okonjima Bush Camp/STD` disambiguates the `STD` every lodge has — an ambiguous name is an error naming the candidates, never a coin flip. The content team's own documentation is the `Bulk Capture Guide` page under Documentation in `/admin`, which renders the column help out of the sheet definitions so it can't drift.

**Re-scrapable sources — how updates are detected.** `scripts/scrape_namibweb.py` (namibweb.com: accommodation, tours, everything the homepage and the `acc*.htm` summaries link to) is the pattern for any source we re-visit rather than import once. It crawls from seeds and decides index-vs-detail by behaviour, so new index pages need no code change; and it answers "what changed since last time?" in three layers: HTTP conditional GET (ETag/Last-Modified per page → 304 = copy the baseline record), per-field content hashes over *normalised* values (so a moved "last updated" line or a rotated ad is not a change, and an image replaced in place under the same filename **is** one — the photo hash covers bytes, not URLs), and a `data/scraped/namibweb_changes.json` diff report of new/changed/missing with per-field before→after. The committed JSON *is* the baseline — without it every record reads as new. A record has to be missing three runs in a row before it counts as gone, and gone is reported, never auto-unpublished.

**Content-source ladder — what may be published, and what replaces what.** `App\Enums\ContentSource` answers two separate questions per listing, for text (`description_source`) and photos (`photos_source` / `pending_photos_source`). **Publishable:** everything except `directory`. A third-party directory's prose and photography stay internal no matter how the pipeline is wired later — editing them does not make them ours, so `Listing::approvePendingPhotos()` refuses to promote directory photos and `ListingController::show` offers no approve button for them (an admin still *sees* them as reference while matching a property). **Rank:** partner/manual (100) > website_scrape (80) > ai_generated (60) > google_places (50) > directory (20), with `null` treated as untouchable — a value from before sources were tracked is not ours to overwrite. Writers compare ranks instead of only filling blanks, so a listing upgrades itself: the website crawler replaces directory prose with the owner's own and stages the owner's photos for approval over a directory photo; `EnrichmentPipeline::needsDescription()` counts directory text as *missing*, so our own generated copy replaces it (bounded by `EnrichmentBudgetGuard`'s daily AI cap). Descriptions we generate are written from the listing's facts, never by paraphrasing a directory — `AIDescriptionGeneratorService` only ever gets the owner's own site as context.

`listings:import-namibweb` consumes that and decides **per field** from two signals: did upstream change it (hash vs. the hashes stored in `scrape_data.namibweb.hashes`), and did *we* change it (column vs. the exact values recorded in `scrape_data.namibweb.imported`). A field we edited — the point, since the plan is to rewrite scraped text — is never overwritten; the upstream value is reported as a conflict instead. Everything namibweb publishes is kept whole under `scrape_data.namibweb` (`upstream` + `raw`) whether or not it is used, so a later decision never means scraping the site again; the scraper likewise keeps the raw HTML (`namibweb_pages.jsonl.gz`) and the photo files as CI artifacts. Nothing from this source auto-publishes: text and photos are namibweb's, so photos land in the `pending_image`/`pending_gallery` review queue and listings are created unpublished. Coordinates are the trusted locator — `city_id` comes from nearest-city GPS matching, and a GPS-only page (many are) gets its address from the scraper's Nominatim reverse-geocode pass.

**namibweb already covers the expansion countries — keep them, filter them.** The source is not Namibia-only: of 2065 archived pages, 1301 are Namibia, **324 Botswana**, 78 South Africa, 44 Mozambique, 25 Zambia, 17 Zimbabwe, plus Lesotho, Eswatini and Malawi. The site states it in the page title's last segment (`Asp Guest House | Bobonong | Central Region | Botswana`), which `extract_country` reads into a `country` field on every record. Nothing is discarded for being foreign — the scraper collects, the importer decides. Namibia is the first market, so today's import filters to it, but when the concept moves to a second country a large part of that country's inventory is already scraped, described and positioned. This is the concrete case behind "don't hardcode country assumptions" above: keep the filter at import time and in config, never in the scraper or the data.

**What a listing page is, decided by measurement.** Prose length does not separate a listing from an index on this site — a small guest house runs to 113 characters of its own text while a regional index runs to 446. The title does: an establishment is titled `<Name> | <Place> | <Country>`, a directory is titled `Travel Directory: …` or `Accommodation by town/area | …`. `is_listing_page` combines the two and guards the families that share the listing title's shape (photo galleries, maps, classifieds, the travel directory). A threshold guessed instead of measured cost about twenty real establishments — Aces Guest House, Khowarib Rest Camp, Purros Camp Site among them — and counted eighteen `acc*.htm` town indexes as listings in exchange.

### Scraper discipline — smallest run that can answer the question
Every request costs someone else's server, and a source that blocks us is lost for good — there is no appeal and no second domain. So a scraper is never pointed at a whole site to find out whether it works.

**The order is fixed: tiny run → validate the actual records → adjust → tiny run again. A full crawl happens only once extraction is proven correct, and it is the last step, not the first.** "Tiny" means bounded by `--max-pages` (a couple of dozen), not only by `--limit`, because a broken classifier can crawl hundreds of pages while producing the two or three records the limit is waiting for.

Concretely, before any full run: the records that come out are read one by one against the live pages they came from — name, address, coordinates, photos, classification — and the crawl's own listing-vs-index ratio is sanity-checked. A ratio that looks impossible *is* impossible; it means the classifier is wrong, and crawling further just multiplies the same mistake.

This is written down because it has gone wrong twice: an entire site crawled to "test", the output then found unusable, and the site crawled again after the fix — the exact pattern that gets an IP banned. Bounded runs also make the fix cheap, since the archive keeps every fetched page (`namibweb_pages.jsonl.gz`, written before any early return) and the classifier and extractors can then be repaired offline against it without touching the source again.

**Documents — the team's own filing cabinet (added 2026-08-12).** `/admin` → Content → **Documents**: a file explorer over a folder tree (`DocumentCategory`, `parent_id`) holding either an uploaded file or a page written in the panel's rich editor (`Document`, `App\Enums\DocumentKind`) — marketing material, business documents, logos, and an internal wiki, with a comment log on each entry through the same polymorphic `Note` table customers and stays use. It is browsed, not listed: the current folder is in the URL (`?folder=`), the breadcrumb walks back up, and **whatever you create is created where you are standing** — that is the whole interaction, so a new screen or action here has to know the current folder rather than ask for one. Folders have no menu entry and no resource of their own; they are made, renamed, moved and deleted from inside the explorer (`ListDocuments`), and a folder with anything in it refuses to be deleted. `document_category_id` is nullable — the top level is a real place to file something, not just a level that holds folders. Two things here are deliberate and should not be "tidied up" into the rest of the media stack. **The files are not on R2.** R2 has no per-object visibility and our media bucket is public, so a contract put there is readable by anyone who guesses the key; documents live on the private `local` disk and leave the server only through `DocumentDownloadController`, whose admin check *is* the access rule. That makes the app server the only copy, so `storage/app/private/documents` is in the nightly backup (`config/backup.php`) — do not drop it. **The wiki editor has no attachment button** for the same reason: a pasted image would land on the public disk. A picture belonging to a page is filed as a document in the same folder — and shows as a thumbnail in the listing, served by that same admin-gated route rather than by the `/thumbs` pipeline, which only resizes objects in the public bucket.

**Ops:** nightly backups + `backup:monitor`; `namibway:fetch-partner-emails` polls the shared mailbox by POP3 every two minutes (never deletes; Roundcube reads the same box by IMAP); `namibway:scrape-websites --limit=10` every five minutes drains the website-crawl backlog (a listing whose `website` changes is marked due by `ListingObserver` clearing `og_scraped_at`, and the sweep takes never-crawled first — costs no AI budget, it reads og:/meta tags and photos from the owner's own site); nightly coordinate backfill; currency conversion with cached exchange rates.

### Cost guards — do not remove
- `EnrichmentBudgetGuard` enforces daily USD caps (`config/enrichment.php`: `places_daily_budget_usd`, `ai_daily_budget_usd`). Built after a redundant-lookup bug burned **~$840 / ~123,500 Google Places calls in a single day** with nothing to stop it. A big one-off backfill may legitimately need more — raise the cap temporarily via env, don't disable it.
- Nightly enrichment (`listings:nightly-enrich`) is **commented out in `routes/console.php` since 2026-08-04** because Claude API costs ran too high. Re-enable with a smaller `nightly_batch_size` once understood.
- Kaia itself stays cheap (~$0.15–0.50 per completed planning session, both phases on Haiku) relative to commission per booking — cost pressure comes from the bulk enrichment pipeline, not from planning.

### Paid work is written down the moment it arrives
The budget guards above cap what we spend. This is the other half, and it is the one that was missing: **what we have already paid for must survive.** A model completion, a Places lookup, a fetched page — anything that cost money to produce is persisted the moment it comes back, before anything else can go wrong.

Not at the end of the flow. Not when the user clicks Save. Not "once the form validates". A result that lives only in form state, session state, a job's local variable or a Livewire component is one navigation, timeout, validation error or bug away from being destroyed — and then we pay a second time for a result we already had. **Cost is not only in the call; it is in the call having to be made twice.**

This is already how the scrapers work — the raw HTML archive is written *before any early return*, so a classifier bug never means fetching the site again. Generalise it: the same reasoning applies to every paid call.

Concretely, when adding anything that spends money:
- **Persist on arrival**, keyed to something durable (a row, a job record), not to the screen that requested it.
- **A multi-step UI writes after each step**, not once at the end. If a user can generate ten AI descriptions and then lose them by closing a tab, the flow is wrong, not the user.
- **Make the write idempotent** so a retry is free rather than a second charge.
- If the result genuinely cannot be persisted yet, say what it costs to redo it in the UI, so nobody discovers the price by losing it.

Broken on 2026-08-16, which is why this is written down: eleven AI-written product descriptions existed only in Livewire form state and were destroyed by the bug in the data-loss section below. The images survived (they had been written to R2 on arrival — the right pattern, in the same feature); only the paid text was lost, because it was the one thing waiting for a Save.

### Data-loss lesson
`namibway:backfill-listing-cities` once overwrote correct `city_id` values because a "Windhoek" hit in a free-text address field (many remote operators use a Windhoek postal address) beat the real location. The command is fixed, but re-running it does **not** repair already-corrupted rows — `restore-listing-city-ids.sh` surgically restores just that column from a backup. Treat any bulk backfill over existing non-null data as destructive: gate on "currently empty" or dry-run first.

**A form may only delete what it was shown (2026-08-16).** The shop product editor is a repeater, so "delete this product" is expressed by a row being *absent*. That makes an empty form indistinguishable from "remove everything" — and the same modal carries import buttons that create products behind it. Open the editor on an empty shop, upload eleven photographs through the nested action, click Save, and the parent form — still holding the empty list it was opened with — deleted all eleven. `ShopProduct` has no soft deletes, so they were gone, and with them the AI descriptions that had cost real money to write.

The fix worth generalising is not "refresh the form after an import" (that is also done, and it is not a guarantee — any concurrent write reintroduces the race). It is that **the delete is scoped to the set of ids the form was hydrated with**, carried in a hidden field: a save may only delete a product it was actually displaying. An empty form now deletes nothing, because a form that saw nothing may say nothing about what should go. Held down by `ShopProductEditorTest`.

This is the same shape as the rule below it — never key a destructive decision on a value that can be stale — with the twist that the stale value here is *absence*. Any "sync a list from a form" write has this bug by default; if you are writing one, ask what happens when the submitted list is empty, and make that case a no-op unless it was explicitly emptied.

A near miss of the same class, found 2026-08-09 before it fired: `photos:audit-r2 --delete-orphaned` decided what was referenced by comparing the raw DB value against `Storage::disk('r2')->url($key)`. Scraper photos are stored as **absolute** URLs built from `CLOUDFLARE_R2_URL` at download time, so changing that variable — exactly what attaching a custom domain to the bucket requires — would have made every referenced photo look orphaned and deleted the entire live library on confirm. It now matches on filename, which no host or prefix change can affect, and which errs toward "referenced" (leaves an orphan) rather than toward deletion. General rule for anything that deletes: never key the keep/delete decision on a value derived from mutable config.

## Standards — use the established one, don't invent a better one
Where a problem already has an industry standard, follow it, even when something bespoke looks tidier. Three reasons, in order of weight: a partner system already speaks the standard, so a connector becomes a mapping instead of a translation; the standard encodes mistakes other people already made and fixed; and "we model it the way the industry models it" is a sales argument in front of an operator who has been burned by a bespoke system before.

Deviating is allowed — the standard sometimes genuinely doesn't fit. Write down why, here, next to the standard it departs from. An undocumented deviation is indistinguishable from not having known the standard existed.

Standards in force:

- **ARI (Availability, Rates, Inventory)** for the lodge booking system. One row per room type per date carrying inventory, rate and stay restrictions (min stay, closed-to-arrival, closed-to-departure); reservations are stay-shaped rows with a quantity; availability is a counter on the date row, changed by an atomic conditional `UPDATE` rather than recomputed. This is how NightsBridge, ResRequest and every channel manager model it. Seasons are ranges *written onto dates*, not a runtime-resolved season entity, so rate resolution stays a pure function of (room type, date) and a stay crossing a season boundary prices per night without special cases. See `App\Services\Inventory`.
- **Half-open date intervals** for stays: a stay ending on the day another begins does not overlap it, so the room turns over the same day. Already the rule in `RoomAvailability`; the calendar follows it.
- **ISO 3166-1 alpha-2** for countries (`regions.country_code`), **ISO 4217** for currency codes.

The deviation that used to sit here — the traveller-facing picker counting overlapping `Inquiry` rows while the lodge counted ARI units — is **half closed since 2026-08-12**. `App\Services\Booking\RoomAvailability` now returns the *smaller* of the two counts, and `App\Services\Booking\RoomOffers` prices the picker from the property's own calendar and rate plan, taxes included. So a stay the lodge took at its own desk stops being offered online, and a season the lodge priced reaches the traveller.

**Closed since 2026-08-12.** A request on a property whose inventory we hold now takes a *provisional stay* on the calendar (`StayPromoter::hold`), released when it is declined or expires and turned into the guest's own stay when it is confirmed — so it is counted once, by the calendar, like everything else. What is still subtracted separately is only what could not take a hold: a partner on somebody else's PMS, a request with no dates, a room that went while the request was in the post. A request that holds its room is excluded from that count *because* it holds it, so the two can never double-count, and the subtraction goes to zero on its own as coverage grows.

Worth being precise about the flooding rule this looks like it contradicts: what that rule protects is **partners being asked to answer speculative requests**, and the one-active-request gate is what enforces it. A room quietly held for a few hours behind a request that already exists asks nobody for anything.

## The core product mechanic — read before touching the booking flow
The central design problem: **turning an AI-generated plan into confirmed bookings without flooding partner owners with speculative requests.**

Status of the governance rules:
- ✅ **One active request pipeline per traveler** — `App\Services\Booking\ActiveRequestGate` matches an active `InquiryStatus` against the booking account *or* the submitted email, checked by `ListingController::storeInquiry` / `storeBatchInquiry` and `TripController::store`; a batch shortlist request checks the gate once for the whole batch.
- ✅ **Real commitment signal before requests go out** — an account plus name, email and travel dates (no payment).
- ✅ **Soft hold with expiry** — Native connector reservations set `hold_expires_at`, take a provisional stay on the ARI calendar (`StayPromoter::hold`, so the room genuinely comes off sale everywhere) and dispatch `ExpireNativeHoldJob`, which releases both the hold and its inventory and mails the guest if the partner doesn't respond in time (idempotent, status-guarded). Declining releases it too.
- ✅ **Low-effort partner response** — signed one-click confirm/cancel URLs (`routes/partner.php`) plus the same transition from the logged-in dashboard, both through `InquiryDecisionService`.
- ⬜ **Staged confirmations** — lock accommodation first, then layer in activities/restaurants once the route is fixed. Still not implemented; today's flow treats each inquiry independently.

### How a confirmed `Inquiry` becomes a `Reservation` — built 2026-08-11 (`App\Services\Booking\StayPromoter`)
`Inquiry` and `Reservation` are not two names for the same thing and must not be merged. An `Inquiry` is the traveller's *request*: it may be declined, it may expire with its soft hold, and it is what the one-active-request gate counts. A `Reservation` is the lodge's *stay*: it holds inventory, has a lifecycle at a front desk, and exists for walk-ins and telephone bookings that never had a request at all.

So the bridge is a one-way promotion, not a sync:

- **When.** At the moment an inquiry reaches `InquiryStatus::Confirmed` — `InquiryDecisionService::confirm()` and the `ProcessInquiry` path that confirms directly. Not before: an `on_request` inquiry is a question, and holding real inventory for every question is the flooding problem this whole mechanic exists to prevent.
- **What is created.** One `Reservation` with `source = website` and `inquiry_id` set, one `reservation_units` row from `Inquiry::bookable_unit_code` resolved against `BookableUnit::code` for that listing, and the nights the writer prices. The inquiry is left exactly as it is — it stays the record of the request, and nothing copies back onto it.
- **Idempotency.** `reservations.inquiry_id` is unique, so a re-confirm, a retried job or a partner clicking the signed link twice cannot produce a second stay. That constraint is the mechanism; do not replace it with a PHP check.
- **The failure that has to be handled.** Promotion can fail where the request could not: the calendar may have no units left. Rare since 2026-08-12 — the picker reads the calendar, and a request holds its room while the partner decides — but not impossible: a request that could take no hold still has a window in which its room can go. A failed promotion must not silently un-confirm the guest's booking; it is an operational alert.
- **Missing dates.** `Inquiry.check_in` / `check_out` are nullable (there is a free-text `travel_dates` field), and a stay without dates cannot be allocated. An inquiry without both dates is not promotable, and that is a validation rule at confirmation time, not a guess.

All of the above is now implemented in `StayPromoter`, and it writes through `InventoryWriter` like every other inventory mutation. Two things the design did not say, decided while building it:

- **Stay restrictions are not enforced on a promotion** (`BookingRequest::$ignoreStayRules`). A minimum stay or a closed-to-arrival day is a rule about *selling* a night; this stay has already been sold and confirmed, and refusing to write it down would leave the calendar lying about how full the property is. Availability is still enforced — an overbooking is a real conflict and becomes the alert above.
- **A request with no `bookable_unit_code`** — most of them, because the picker only appears once a property has entered its rooms — takes the property's single active room type when there is exactly one, and is refused as a guess when there is more than one.

### What a restaurant is asked for — added 2026-08-16 (`App\Enums\InquiryKind`)
Every listing type used to be asked the same question: check-in, check-out, adults, children. A restaurant has no departure date, and the two things it actually sells could not be expressed at all. So an `Inquiry` now declares its own **kind** — `booking` (a stay: accommodation, activity, vehicle), `table_reservation` (one date, one **time**, a party) or `order` (menu items and quantities, and nothing else).

This is deliberately a property of the *request*, not of the listing's vertical — `BOOKING_BEYOND_ROOMS.md` §6 warns against the core learning to ask "which vertical am I serving?", and "what shape is this request?" is a different and answerable question. Rules worth not breaking:

- **The kind is the server's decision, not the form's.** `Listing::requestKinds()` is the single answer to "what may this property be asked for?", and both halves read it: the page draws its tabs from it, and `ListingController` enforces the same list on the POST, so the two cannot disagree. Which fields are required — and which are dropped — then follows from the kind, so an order can never carry a check-in nobody asked for.
- **A restaurant says which of the two it takes online** — `listings.accepts_table_reservations` and `accepts_orders`, both default true, both under `accepts_inquiries` and both meaningless on any other listing type (`App\Filament\Support\RestaurantChannelSchema`, shown in both panels). They exist because both channels used to be *derived*, and both derivations conflated having something with selling it over the internet: every restaurant was offered for a table with no way to say "walk-ins only", and entering a menu silently switched ordering on. **A menu has two jobs — telling somebody what there is, and being orderable — and only the second is a commercial commitment.** With ordering off the card still renders on the listing, as something to read; ordering on additionally needs a non-empty menu, because a switch over an empty menu is a promise the page cannot keep.
- **The browser sends ids and quantities. Nothing else.** `App\Services\Booking\MenuOrder` reads every name and price from `menu_items` in the database and freezes them onto `inquiry_items` with the line total; the running total on the page is a display. A form that accepts a price is a form somebody can edit to post a different one.
- **`menu_items` is not `bookable_units`, on purpose.** A room type is a thing with a count and a calendar; a plate of kudu has neither, and putting it there would mean inventing a unit count and then teaching `InventoryWriter` to ignore it. It is a small table at the edge and the booking core never learns it exists. A restaurant's real inventory — covers per sitting — is a slot on the ARI calendar when it is built, and is not this.
- **Only a `booking` becomes a stay.** `InquiryKind::becomesAStay()` is what `StayPromoter` checks first; without it every confirmed table booking would fail promotion for having no check-out and mail the team an incident. An alert that fires on a normal day is one nobody reads on the day it matters.
- **`inquiries.arrival_time` is the one place a requested time lives.** The customer-website enquiry form used to fold it into the free-text `travel_dates` ("2026-09-01 at 19:30") to avoid a migration; with two front doors asking for it, both now write the column and `SiteEnquiryController` stops folding.
- **A restaurant request is outside the one-active-request gate**, in both directions — it neither blocks nor is blocked (`ActiveRequestGate` filters on the same `becomesAStay()`). What that rule rations is a plan's worth of speculative requests at lodges who each have to answer one; a table on Thursday and a plate of food go to a single business that can answer today. Counting them would have meant ordering dinner locked a traveller out of requesting anywhere to sleep — not a rule anybody wrote down, just the gate's original assumption that every request is a stay outliving the day it stopped being true.

### Who a request is for — added 2026-08-16
`inquiries.listing_id` used to be NOT NULL, which said that every request is about a property on the travel platform. A shop selling goods through its own customer website has no listing and never wanted one, so it could receive nothing at all. A request now names a **listing or a partner** — `partner_id` is nullable, a CHECK constraint (`inquiries_have_a_seller`) refuses a row that names neither, and `Inquiry::seller()` / `sellerName()` / `sellerEmail()` is the one reader. **Do not write `$inquiry->listing->name` again**: a dozen call sites did, mail views included, and every one of them fatalled the moment a request arrived without a listing. `sellerEmail()` resolves partner → listing's partner → listing's contact address, in that order, because the partner is the account that logs in and owns the signed confirm and decline links.

### The contact form on a customer's website — added 2026-08-16
`App\Sites\Blocks\EnquiryFormType` is what the one form on a customer site asks for: contact, stay request, table reservation, restaurant order, product order. **Exactly one per site** — a page offering three ways in has not decided what it sells. It is deliberately *not* `InquiryKind`: that is what the stored request is, three shapes the whole platform understands; this is a presentation choice one owner makes, and several types produce the same kind. Rules: **the type is the block's, never the POST's** (the hidden field records what the visitor was looking at, nothing more), the required fields follow from the type, **email or WhatsApp but never both**, and an order is priced by `SiteOrder` from the business's own rows exactly the way `MenuOrder` prices one on namibway.com. `shop_products.price` is a real number for that reason; `price_text` is the "Call for price" fallback, and a product with only text is shown but not orderable.

Two rules the same day cost a real site: **read the type through `EnquiryBlock::formTypeFor()`, never `formType()`** — the stored value was set at generation and a restaurant that has since switched `accepts_orders` on and `accepts_table_reservations` off must not still be offering a table; the correction happens at render, so it needs no migration and keeps applying. And **the contact form has one name**: the menu item, the button beside it and the strip at the foot all ask `SiteActions`, because a menu reading "Request availability" next to a button reading "Book a table" pointed at the same form. Details and the open payment question: `PROJECT_STATUS.md` § 4, entries of 2026-08-16.

### The customer — one of the few main entities, added 2026-08-11
A booking system has a small number of nouns that everything else hangs off, and the customer is one of them. `customers` is scoped to the **partner** (NWR's twenty camps share their guests; another lodge keeps its own record of the same person), and somebody is recognised by **`user_id` first, then email** — an account survives a change of address and an email does not. The phone is stored normalised and searchable but is deliberately *not* a match key: a couple's single mobile merging two people is much harder to undo than two records.

Rules that are load-bearing: **every booking resolves a customer** inside `InventoryWriter::book()`, so the customer view has no holes; **an existing customer is used, not overwritten**, so a typo in one booking cannot rewrite what the property learned over three seasons; and the frozen `guest_name`/`guest_email`/`guest_phone` on the reservation stay exactly as typed — the link says whose stay it is, the strings say what the booking said. Email is required on the website and optional at the desk, because a mandatory field that cannot always be satisfied produces `x@x.com`.

Comments live in a polymorphic `notes` table with the author's name frozen beside the account id, for customers and stays alike. `reservations.notes` is a different thing and stays: that column is what the booking was taken with, this table is the running log that starts afterwards.

### The money side — built 2026-08-12 (`app/Services/Payments`)
The design is `PAYMENTS.md` and the guide staff read is **Documentation → Payments Guide** in `/admin`. What follows is only the handful of rules that a future change can quietly break, all of them enforced by something rather than remembered:

- **One write path, exactly like inventory.** Everything that inserts into `payments` goes through `PaymentRecorder`, guarded by `MoneyWriteGuard` at runtime and by `MoneyWritePathTest` scanning the source for `DB::table('payments')` and `Payment::create(` outside it. Same two-layer shape as `InventoryWriteGuard`, for the same reason.
- **Nothing is ever edited.** A payment entered wrongly is *reversed* — a negative row pointing back at it, both rows kept — and re-entered. The only mutation is the status, one-way: recorded → cleared or recorded → failed. **A reversal takes the status of the row it reverses**; hardcoding it to cleared produced a negative "confirmed" figure on the folio (fixed 2026-08-12).
- **Every money comparison is in whole cents** (`Money::cents()`), never on the floats the decimal columns cast to.
- **Invoice numbers are gapless per property**, taken with `SELECT … FOR UPDATE` on a counter row inside the issuing transaction — never `max()+1`, never an auto-increment, because a tax authority asks about the gap and "the transaction rolled back" is not an answer. An issued invoice is immutable; the only correction is a credit note, and `invoices.corrects_invoice_id` is unique so it can only happen once.
- **Idempotency is a unique index, not a PHP check** — `payments.payment_intent_id` is unique, so a gateway retrying its callback cannot pay a stay twice.
- **The settlement model is derived, never stored.** `SettlementModel::forDepositRate()` reads it off the deposit share: 0 % → agency, 100 % → merchant, anything between → split. There is no settlement-model column and adding one would let it disagree with the number it describes. Commission is ours and the deposit is the partner's; both resolve listing → partner → platform setting → config, with null meaning inherit.
- **Rates are frozen onto the reservation at booking**, like the price. An older booking showing no payment link is correct, not a bug.
- **Nothing above the `PaymentProvider` interface may name a gateway** — a test greps for it. Provider-specific behaviour belongs in the provider.

## AI engine notes

## Partner landscape
**No partner is live yet.** Every connector is written against documented/expected behaviour and has never run against a real partner account — treat all of them as unvalidated, and expect the first real integration to turn up surprises.
